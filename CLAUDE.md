# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Unity **6000.4.10f1** 2D (URP) programming game (working title "CodeRogue" in `CreateAssetMenu` paths). The player doesn't control the pawn directly — they write **Lua** in in-game editor windows, and Lua calls C# commands that move the pawn, query objects, etc. Every Lua construct costs "energy". Art comes from the third-party `Assets/Tiny Swords` pack — don't modify it. All project code lives in `Assets/_Game`; the only scene in the build is `Assets/_Game/Scenes/Game/SampleScene.unity`.

**Target design & plan:** `Docs/GameDesign.md` (agreed vision of the final game: roguelike runs ↔ hub, world threat, achievements unlocking commands/language constructs, tutorial, puzzle structures — plus open questions) and `Docs/Roadmap.md` (staged checklist, ★ = scope for the 2026-10-26 slice). Check new features against them and tick off Roadmap items when done.

Key dependencies: Lua-CSharp 0.5.5 (`Lua`, `Lua.Standard` namespaces; DLLs installed by NuGetForUnity into `Assets/Packages`, Unity glue via the `com.nuskey8.lua.unity` UPM package), UniTask, UI Toolkit (UXML/USS, no uGUI), Input System, Tilemap + Rule Tiles. Binary assets (png, dll) are in Git LFS.

## Build / verify

There are no tests, asmdefs, or lint setup. All game code compiles into `Assembly-CSharp`.

- Fast compile check without opening Unity (uses the Unity-generated, gitignored csproj):
  `dotnet build Assembly-CSharp.csproj -nologo -v q`
  The csproj lists files explicitly and is only regenerated by Unity — a **newly added** `.cs` file won't be compiled by this command until Unity regenerates the project (or you add a `<Compile Include>` line locally).
- Real verification requires Play Mode in the Unity editor.

## Architecture

**Composition root:** `Core/Level.cs` holds serialized references to every system and wires them in `Awake` in a fixed order: map generation → spawn point → player instantiate → `PlayerCommandExecutor` → fog of war → camera → objects → run state (`RunModifiers`, `PlayerEnergy`, `PlayerHealth`, `PlayerInventory`) → structures → `DayCycle` → enemies (`EnemyManager`, `CombatService`) → puzzles (`PuzzleManager`, `PuzzleGenerator`) → `LuaSandbox` → UI → `RunController`. Systems don't find each other; dependencies are passed via `Initialize(...)` methods, mostly as interfaces (`IMapDataProvider` implemented by `TilemapGenerator`, `IPlayerDataProvider` implemented by `PlayerConfig`). When adding a system, add a serialized field + assert + an `Initialize` call here.

**Events:** three static buses — `PlayerEventBus` (player moved, UI focus, camera, day start/end), `UIEventBus` (energy, per-window code cost, inventory, notifications) and `GameEventBus` (gameplay events for achievements, see below). `UIManager` is the single subscriber that pushes `UIEventBus` changes into UI elements. Because the buses are static, always unsubscribe in `OnDestroy` with named methods (not lambdas).

**Config:** tunables are ScriptableObjects in `Assets/_Game/ScriptableObjects` (`PlayerConfig`, `EnergyConfig`, `MapGenerationConfig`, `CodeEditorTheme`, `ResourceVariant`s).

**Lua pipeline** (`Scripts/Lua`):
- A command = class deriving from `LuaCommandBase` (or `PlayerCommandBase`, which adds `Executor` and `MapData`). It declares `Name`, `EnergyCost`, `Signature`, `Description` and overrides `ExecuteAsync(context, ct)` (return the number of values passed to `context.Return`). The base `Register(state, meter)` charges `EnergyCost` through `EnergyMeter` on **every call**, then runs `ExecuteAsync`. No command may be free: `EnergyCost` must be > 0 (asserted on registration); functions a command hands back to Lua (e.g. `getNear` on the `findObjects` result) charge through the protected `Meter` too. Pass `ct` into any awaited executor call so Stop/cancellation works.
- New commands must be registered in `LuaSandbox.RegisterCommands()` (via `AddCommand`).
- Design rule: basic commands are cheap; convenience ("ready-made") commands such as `obtain([type])` do what a short snippet of basic commands does but cost more than that snippet, so writing your own code saves energy. They must reuse the same services (e.g. `ResourceHarvester`) so physical costs are identical.
- `autoExplore([type])` (10): the target comes from `ExplorePlanner` (pure static, EditMode-tested) — of the 8 directions the one whose ≤ 6-tile straight walk (water stops it, like `MoveAsync`) reveals the most never-seen land (`IFogProvider.IsExplored`, vision square around each path tile); if none reveals anything, BFS over land (radius 20) to the nearest unexplored tile and walk to the farthest point of that path (≤ 6 steps) reachable in a straight line. Ties are broken by a hash of map seed + tile + direction (no `Random`). Returns the number of land tiles actually revealed (`0, reason` if there is nowhere to go). With a type (resource / enemy / puzzle, parsed like `findObjects`) it repeats steps (max 3) until one is in sight and returns the nearest table (as `getNear`) or `nil, "not found"`; the first step is in the call price, each further step charges another 10 through `Meter` (out of energy stops the run, like any charge).
- `LuaSandbox.ExecuteAsync`: auxiliary editor windows are wrapped as global functions `function <WindowTitle>(...) <code> end` (so window titles must be valid Lua identifiers — enforced by `LuaIdentifierValidator` in `TitleEditor`), then the main window code runs. Execution is cancellable (`Stop()`, the Run button toggles to Stop) and guarded by a thread-pool watchdog that cancels if the main thread is blocked longer than `freezeTimeoutSeconds` (catches infinite loops without awaits).
- Energy is spent at **runtime**, for what actually executes; nothing is charged on Run. `EnergyInstrumenter` rewrites each chunk before execution (no newlines added, so line numbers stay): `if/elseif/while/until` → `kw __energy(c) and cond` (every condition check), `for … do` → `do ;__energy(c);` (every iteration), `function f(…)` (named, local, anonymous, and the aux-window wrappers) → `functionCost` on every call, `local`/`return`/`else` → charge per execution. Costs come from `EnergyConfig` (only the keyword costs; command prices are `ILuaCommand.EnergyCost`). `__energy` and command calls go through `EnergyMeter`; when energy runs out it throws, stays exhausted (so `pcall` can't swallow it) and cancels the run with an "out of energy" result. Syntax is checked on the original code first (`LuaState.Load`) so compile errors point at the player's code; chunks are named `Main` / window title. The tokenizer handles `--[[ ]]` / `[[ ]]` long brackets — keep it exact (the instrumenter refuses to rewrite code it can't re-assemble).
- Current-line highlighting: `LuaLineTracker` (created in `LuaSandbox`, set as `EnergyMeter.LineTracker`) is probed by `EnergyMeter.Track(state)` from every command wrapper (`LuaCommandBase`) and `__energy` — the calling Lua frame gives `Proto.ChunkName` (window) and `LineInfo[CallerInstructionIndex]` (no allocations; aux windows −1 for the wrapper line). `LuaSandbox.OnExecutingLineChanged(window, line)` fires on change, `(null, 0)` at run start/end; `CodeEditorManager` redraws at most every 50 ms via `CodeEditorWindowBase.SetActiveLine` → `CodeEditor` draws a bar behind the line (`CodeEditorTheme.activeLineColor`, line height measured with `MeasureTextSize`) and colours the line number. Tests: `LuaLineTrackerTests`.
- `EnergyCounter` computes the same costs statically per line/window for display: it's the price of one pass, loops multiply it. Physical actions (harvest durability, craft energy) are charged separately by their services.
- Unlocks: `UnlockRegistry` (plain class created in `Level` from the `UnlockConfig` asset `DefaultUnlockConfig` + `MetaProgress`): unlocked = starting set ∪ saved (`unlockAll`/missing config = all; debug only — off in `DefaultUnlockConfig`, achievements grant the rest). `UnlockCommand`/`UnlockConstruct`/`UnlockRecipe` save immediately and raise `OnUnlocked(UnlockKind, id)` on first unlock (unknown commands are saved as deferred, without the event; unknown construct ids are rejected with a warning — the construct set is closed). `LuaSandbox` keeps all commands in `AllCommands` but only unlocked ones in `Registry` (help/highlight/completion/EnergyCounter never see locked ones); locked commands get a Lua stub erroring "command `x` is not unlocked yet" (no energy). Unlocks during a run apply after it ends, then `OnUnlocksApplied` fires and `CodeEditorManager` rebuilds help, highlighter API names, line costs and class-window availability. Construct ids in `LuaConstructs` (`local`, `if`+elseif/else, `for`, `while`, `repeat`+until, `function`, `classes` = auxiliary windows); `goto` and `::labels::` are forbidden permanently (they'd be free loops); break/return/and/or/not/do are never locked. After the syntax check of all windows and before instrumenting, `LuaConstructGuard` scans each window's original code by tokens and refuses with e.g. "loop `for` is not unlocked yet (Main, line 3)"; aux windows with code while `classes` is locked are refused. No energy is spent, but the refusal counts as a day run, like a compile error (intended). Locked keywords are drawn with `CodeEditorTheme.lockedKeywordColor`.
- The sandbox strips `load`, `loadfile`, `dofile`, `require`, `package`, `io`, `debug`, `collectgarbage` after `OpenStandardLibraries()` and leaves only `os.clock/time/date` — loading code from strings would bypass the guard and the energy instrumenter. `LuaModuleLoader` exists but is not wired in. The standard `print` is removed too: `print(...)` is `PrintCommand` (0.5, unlocked by `first_bug`; locked = the usual stub) — args joined by tabs, tables one level (`{1, x=3}`, nested `{...}`), a `findObjects` list as `list(count=N) {first 3, ...}`, output capped at `PrintCommand.MaxLength` (200); it goes to `LuaSandbox.OnLogMessage(string, LogEntryType.Info)` (main thread, during the run) for the main-window log. `getStatus().spent` = `LuaSandbox.EnergySpentThisRun` (`PlayerEnergy.TotalSpent` delta since the run started, same as `CodeRunReport.EnergySpent`).

**Hub ↔ run & meta progress:** `GameSession` (static) keeps the requested `GameMode` (Hub/Run) and the lazily loaded `MetaProgress` across scene loads (statics are reset in `SubsystemRegistration` for Play Mode without domain reload). Every transition reloads the scene (`GameSession.StartRun`/`ReturnToHub`), so each run starts clean with a new random seed; the first load uses `Level.startInHub`. The hub UI (`RunScreens` + `HubPanel.uxml`) is side panels over the visible hub grid (stock + Start Run on the left, buildings on the right — see UI); `RunScreens` also has the exit confirmation and the run summary; the hub world (building grid) is drawn on the generated map — see "Hub buildings" below. `RunController` (plain class created last in `Level`) handles the TopBar Exit Run button (not while code runs; confirmation inside the UI) and `PlayerHealth.OnDied` (stops the code): it builds a `RunSummary`, moves only items with `ResourceItem.IsMaterial` (`MaterialResource`) to the hub stock — nothing on defeat — and saves `MetaProgress` immediately, before the summary is shown. `MetaProgress` (`meta_progress.json` in `persistentDataPath`, written only by `Save()`) stores unlocked commands/constructs, achievements, events, tutorial flags, hint setting, hub material stock (keyed by `itemId`, else asset name) and hub buildings; `JsonFileStore` does the atomic write / `.bak` on a broken file for it and `CodeLibrary`. Reset: `MetaProgress.ResetAll()` (copies the file to `.reset.bak`, writes empty progress, hints on; `CodeLibrary` untouched) via `GameSession.ResetProgress()` (hub Reset progress button, second click within 3 s confirms → reload into the hub) or the editor menu `CodeRogue/Reset Meta Progress` (outside Play Mode `MetaProgress.ResetFile` moves the file to `.reset.bak`). `RunModifiers.Create(PlayerConfig, MetaProgress)` holds per-run values (base energy limit, max health, inventory slots, runs per day, threat day, starting items) — run systems read these, not `PlayerConfig`; `Create(config, progress, catalog)` adds the effects of built hub buildings (catalog = `Level.hubBuildingCatalog`; without it — base values only). `PlayerHealth` (plain class, `UIEventBus.OnPlayerHealthChanged` → TopBar bar, `health`/`maxHealth` in `getStatus()`) takes damage from enemies and is healed by sleeping.

**Hub buildings (stage 4, `Scripts/Hub`):** `HubBuildingDefinition` SO (`CodeRogue/Hub/HubBuilding`: id `storage`/`shrine`/`watchtower`/`healer_hut`, title, description, `sprite` or `prefab`, `size` in cells, `cost` as `ItemStack`s — always read through `GetCost()` (merged, keys = `MetaProgress.GetItemKey`, like the hub stock), `effects` {`HubEffectType` EnergyLimit/ThreatDays/InventorySlots/MaxHealth/RunsPerDay, amount; add new types only at the end}) collected in one `HubBuildingCatalog` (`CodeRogue/Hub/HubBuildingCatalog`, also holds `gridSize` 8×6) on `Level` (null = warning: nothing to build, no bonuses). `Level` passes the catalog ids to `UnlockRegistry.SetKnownHubBuildings` in both modes (unlocks are achievement rewards and happen in runs). Only in Hub mode `Level.InitializeHub` creates `HubService` (plain class: `Definitions`, `CheckAvailability` Unknown/AlreadyBuilt/Locked/NotAffordable, `CanAfford`, `IsInBounds`/`IsAreaFree`/`CanPlaceAt`, `CheckBuild`, `GetPlaced`, `GetPlacementAt`; `TryBuild(def, cell)` takes the cost from the `MetaProgress` stock (`RemoveMaterial`), records `PlacedHubBuilding {buildingId, x, y}` (cell = bottom-left of the footprint, (0,0) = bottom-left of the grid; one building per id, no demolition), `Save()`s, publishes `GameEventBus` `HubBuildingBuilt` (Id = building id) and `OnBuilt`; `Describe(result)` gives the English refusal text), `HubGrid` (plain class, root GameObject "Hub": a plaza of runtime square sprites at orders 20–21 — above tilemaps, below objects — over the generated map, placed by `ChooseOrigin` above the spawn tile so the player stands at its bottom edge; fog over it is revealed via `FogOfWarSystem.RevealRect`, map objects on it are deactivated, the camera is put on `WorldCenter` with `CameraController.FocusOn`; building views = sprite scaled to footprint width, base on the footprint's bottom edge, `DepthSortedSprite`; `WorldToCell`/`CellToWorld`/`TryScreenToCell`/`GetPlacementCell`, `ShowGhost(def, cell, valid)`/`HideGhost` at overlay order −10) and `HubPlacementController` (MonoBehaviour on the hub root: `Begin(def)` → the ghost follows the mouse, LMB = `TryBuild`, RMB/Esc = `Cancel`, ignored over UI via `IPointerOverUIProvider`; `OnPlaced`/`OnCancelled`/`OnFailed`). Exposed as `Level.HubService`/`HubGrid`/`HubPlacement` (null in Run mode). Tests: `Tests/Editor/HubServiceTests`.

**Achievements & GameEventBus:** `GameEventBus` (static, handlers reset in `SubsystemRegistration`, handler exceptions are logged, not rethrown) publishes `GameEvent {Type, Id, Tag, Amount, Recycled}` from where things actually happen: `Harvested` (`ResourceHarvester` pick-up, so `obtain` counts too; Id = item key, Tag = object type), `Mined` (Id = object type), `ItemObtained` (`PlayerInventory.Add`/`TryExchange`), `Crafted` (`CraftCommand`), `Built` (`StructureManager.TryPlace`), `DayPassed` (`DayCycle`), `CommandUsed` (`LuaCommandBase.Register`, every paid call), `ConstructUsed` (once per run per construct found by `LuaConstructGuard.Check(..., used)` in a run that passed the checks), `RunStarted`/`RunFinished` (`LuaSandbox`, plus `OnRunStarted`/`OnRunFinished(CodeRunReport)` with energy spent = `PlayerEnergy.TotalSpent` delta, i.e. everything incl. mining/crafting; `RunFinished` Id = `success`/`failed`, Tag = `CodeRunReport.Outcome` (`GameEventBus.RunTag*`): `ok`, `error` (compile/runtime error, incl. command errors reaching the top), `energy` (out of energy, even if `pcall` caught it), `stopped` (Stop, death, watchdog), `locked` (`LuaConstructGuard` refusal or an uncaught locked-command stub) — `first_bug` filters `error`). `HubBuildingBuilt` (`HubService.TryBuild`, Id = building id). `ThreatReached`, `EnemyFound`, `EnemyKilled`, `FoodEaten` are published by their systems (see GameEventBus.cs / the sections above); `PuzzleSolved` exists in the enum only (stage 6). Item ids are `MetaProgress.GetItemKey`. `Recycled` = not new loot (picking up objects spawned by `drop` — `ResourceObject.DroppedByPlayer`, reset by the pool — and run starting items); achievements ignore such events. Definitions: `AchievementDefinition` SO (`CodeRogue/Achievements/Achievement`: id, title, description, icon, `AchievementCondition` {type Counter/EfficientGather/FirstUse, gameEvent, filter matched against Id or Tag case-insensitively, empty = any, amount, maxEnergy}, rewards `{kind Command/Construct/Recipe/HubBuilding/MapEvent, id}`), collected in one `AchievementCatalog` on `Level` (null catalog = warning, no achievements). `AchievementTracker` (plain class created in `Level` after `LuaSandbox`, disposed in `Level.OnDestroy`) works in hub and run: Counter/FirstUse progress lives in `MetaProgress.achievementProgress` (saved at the end of every code run, day and on dispose — not per event); EfficientGather counts within one code run and is checked at the moment `amount` is reached (spent since run start ≤ `maxEnergy`); it only counts events with `GameEvent.FromThisRun` — `GameEventBus.ActiveRunId` numbers code runs, `ResourceHarvester.DropLoot` stamps `ResourceObject.SpawnRunId` (reset by the pool), so picking up loot mined in an earlier run (or world objects) does not count; counters are unaffected. On completion: `MetaProgress.CompleteAchievement`, rewards through `UnlockRegistry`, `Save`, `OnAchievementCompleted` (the UI shows a toast — no `UIEventBus` notification); API for UI: `Definitions`, `GetProgress`, `IsCompleted`, `CompletedThisScene` (→ `RunSummary.Achievements`), `OnProgressChanged`; exposed as `Level.AchievementTracker`. `UnlockRegistry` also handles recipes (`CraftRecipe.locked` + `MetaProgress.unlockedRecipes` by result key; `craft()` says "recipe `x` is not unlocked yet", `CraftingPanel` hides locked ones and rebuilds on `OnUnlocksApplied`), hub buildings (`unlockedHubBuildings`) and map events (`unlockedEvents`); `OnUnlocked` fires for every kind, but hub buildings / map events are saved as deferred (no event) until their catalogs are passed via `SetKnownHubBuildings`/`SetKnownMapEvents` (stages 4/6). Unlocking a command/recipe the game doesn't have yet (rewards of later stages, e.g. `attack`, `sword`) is deferred: it is saved without an event and becomes available once the command/recipe exists. Rewards of already completed achievements are re-granted (idempotently) by `GrantRewardsOfCompleted()`, which `Level` calls after the UI is initialized (so `UnlockPopup` sees them). On death while code runs, `RunController` stops the run and builds the summary only after `OnRunningChanged(false)`, so achievements completed in the stopped run's `finally` are included. `craft()` spends the recipe energy before `TryExchange` (refunded via `PlayerEnergy.Refund` if the result doesn't fit).

**Day cycle & energy budget:** `DayCycle` (plain class created in `Level`, attached to `LuaSandbox.OnRunningChanged`) gives `RunModifiers.RunsPerDay` (3) runs per day — every finished run counts, errors and Stop included; after the last one (or the End Day button, not while running) the day ends: `PlayerEnergy.SetMax(max, refill)` with max = `RunModifiers.BaseEnergyLimit` − penalty (`base × energyPenaltyMultiplier` if the day ended with < 1 energy, next day only) + bonus (`homeBonusPerDay` × consecutive nights ended near a `Structure` with `isSleepingPlace`, capped at `maxEnergyBonus`), clamped to `minEnergyLimit`. State goes to the top bar through `UIEventBus.OnDayChanged(DayInfo)`; Lua reads it with `getStatus()`. Energy is the per-day budget: language constructs are cheap (`EnergyConfig`: loop iteration/check 1, `if` 0.5, function call 0.5 — not 0, otherwise recursion through `and` (`return n > 0 and f(n - 1)`) would be a free loop; `local`/`return`/`else` 0), world actions are the main sink. Food (later) is meant to add energy. A night near a sleeping place also heals `PlayerConfig.sleepHealAmount` (15) via `PlayerHealth.Heal`.

**Threat, enemies & combat (stage 3, `Scripts/Enemies`, spec — GameDesign §10.1):** `DayCycle` exposes `ThreatDay` (`RunModifiers.ThreatDay`), `DaysUntilThreat` (0 = active), `IsThreatActive`, mirrored in `DayInfo` (`ThreatDay`/`DaysUntilThreat`/`ThreatActive`); at the start of day `threatDay − 1` it posts a warning notification, on day `threatDay` (or on `Attach` if it is 1) — `GameEventBus` `ThreatReached` once per run + `OnThreatReached`; every new day raises `DayCycle.OnDayStarted(day)`. **World time runs only while code runs:** `EnemyManager` (plain class created in `Level` after `DayCycle`, `Attach(luaSandbox)`, `Dispose()` in `Level.OnDestroy`, instances under a runtime "Enemies" GameObject, exposed as `Level.Enemies`) starts a UniTask clock on `OnRunningChanged(true)` and ticks every enemy each frame until the run ends; between runs nothing moves or cools down. The first `EnemyConfig.runStartGrace` (0.5 s) of every run enemies don't hit. `Enemy` (MonoBehaviour on the prefab: non-trigger `Collider2D` at the feet, auto `DepthSortedSprite` Dynamic, Rigidbody2D forced Kinematic if present) keeps a free map `Position`, `Home` (post / patrol spawn point), stable int `Id` (1.. per run, not `GetInstanceID`), `TypeId` (`EnemyDefinition.enemyId`, e.g. "goblin"), `Health`/`MaxHealth`, `State` (+ `StateName` for Lua: idle/patrol/chase, returning = patrol), `IsVisible`; `TakeDamage(int)` → at 0 `OnKilled` → `EnemyManager` drops `EnemyDefinition.loot` on the ground via `worldPrefab`/`ObjectManager.Spawn` with `SpawnRunId = ActiveRunId` (no prefab → inventory), publishes `EnemyKilled` (Id = type, Tag = guard/patrol) and returns it to the pool (keyed by prefab). Behaviour: aggro radius → chase (chase speed) up to `leashRadius` from `Home`, inside `attackRadius` (centre to centre) a windup then a hit every `attackCooldown` on `PlayerHealth.TakeDamage`; chase resets when the player is farther than `loseChaseDistance` or the enemy is beyond the leash, then a guard walks back (patrol speed), a patrol keeps walking to random land points ≤ `patrolPointRadius` from `Home`, waiting `patrolWaitSeconds`. Movement is a straight line with the player's collision approach (`Collider2D.Cast` + slide, water blocks per axis), no pathfinding. Stats: `EnemyDefinition` SO (`CodeRogue/Enemies/Enemy`; 0 = take the default from `EnemyConfig`, resolved into `EnemyStats`); `EnemyConfig` SO (`CodeRogue/Enemies/EnemyConfig`, on `Level.enemyConfig`; null = no enemies, warning): guard/patrol kinds, `camps` (`EnemyCampSpec` count / min distance from spawn / `campValuablePrefab` such as `gold_ore` in the centre, spawned through `ObjectManager.Spawn`), `minCampSpacing`, `campRadius`, patrol counts (`min(patrolsOnThreatDay + growth × (day − threatDay), maxNewPatrolsPerDay)`), spawn ring under fog (`patrolSpawnMin/MaxDistance` from the player, fallback — any land that far), defaults. Camps are generated only in `GameMode.Run`, after objects, deterministically from `IMapDataProvider.Seed` (patrols — from seed + day), on land under the whole footprint, away from objects/enemies/colliders. Enemies on tiles that aren't `IFogProvider.IsVisible` have renderers off but still act; the first time an enemy is on a visible tile in the run `EnemyFound` is published (`EnemyManager.RefreshVisibility`). Queries: `Enemies`, `GetEnemyById`, `GetEnemiesInRadius(mapPos, r)` (nearest first), `GetEnemiesAtTile`, `GetNearestEnemy`, events `OnEnemySpawned/Killed/Spotted`, `OnPlayerAttacked`. Combat: `WeaponItem : ToolItem` (`toolType` always `Sword`, `damage` 15, `attackRadius` 1.5, wear per hit, never stacks), `PlayerInventory.FindWeaponSlot()` (highest damage, then most worn); `CombatService` (plain class created in `Level`, like `ResourceHarvester` — the Lua `attack` wraps it): `TryAttack(enemy, out result, out error)` / `TryAttackNearest` / `TryAttackAt(point)` / `AttackAsync(enemy, ct)` (hit immediately, then waits `StrikeDuration` 0.5 s), distance from `PlayerCommandExecutor.Position` (exact map position; `MapPosition.FromWorld`) to the enemy ≤ weapon radius, fist = 5 damage / 1.5 tiles. A hit costs no extra energy — only the command call. **Lua side:** `LuaSandbox.Initialize(..., enemies, combat)` (both may be null in tests). `attack([enemy | x, y])` (`AttackCommand`, 2 energy, not in the starting set — reward of `enemy_spotted`): enemy table → `GetEnemyById` (by id, the enemy may have moved), `x, y` → nearest enemy within 0.75 of the point, no args → nearest within `CombatService.AttackRadius` of the player; awaits `CombatService.AttackAsync(target, ct)`; returns `true, damage, killed` or `nil, reason`. `findObjects("enemy")` (all) / `findObjects("goblin")` (by `TypeId`; unknown names that are neither object types nor enemy types on the map error) list only alive enemies with `IsVisible`; enemy tables: `id` = `LuaObjectList.EnemyIdOffset` (1e9) + `Enemy.Id` (runtime `GetInstanceID`s of objects are negative, so ids never collide; `LuaObjectList.TryGetEnemyId` decodes), `kind` = "enemy", `type` = `TypeId`, `x`, `y`, `health`, `maxHealth`, `state`, `durability` = 0, `distance` (from the exact `PlayerCommandExecutor.Position`, as `CombatService` measures it; objects use `CurrentTile`), no `tool`. List methods work on mixed lists, skip dead enemies (entry keeps the `Id`, so a pooled enemy reused as another one counts as dead) and read enemy `x`/`y`/`health`/`state`/`distance` live. `harvest`/`mine` on an enemy table, or on a point with no resource but an enemy (`AttackCommand.GetNotHarvestableError`), and `obtain("goblin")` fail with "… use attack()". `moveTo(x, y)` also accepts any table with `x`/`y` (`HarvestCommand.TryReadPoint`). `getStatus()` adds `threatDay`, `daysToThreat` (0 = active), `threat` (bool).

**Depth sorting:** `DepthSortedSprite` sets `sortingOrder` of all child `SpriteRenderer`s from `transform.position.y` via `DepthSorting` (bottom of map = 1000, top = 100; range configured in `Level` right after map generation). `ResourceObject` adds it automatically and refreshes on `SetPosition`; the player gets it in `Level.SpawnPlayer` with `Dynamic = true`. The fog tilemap is forced to `DepthSorting.OverlayOrder` (2000) so it stays above all objects — keep any new world sprites inside 100–1000 and overlays above.

**Player movement:** `PlayerCommandExecutor` keeps the logical `CurrentTile` and animates tile-by-tile with UniTask; walkability comes from `IMapDataProvider`, and movement is continuous (`MoveTowardsAsync`): the target is the last land tile on the straight line (water stops immediately), and each frame the player's own non-trigger `Collider2D` is cast (`Collider2D.Cast`, its real feet shape) against other non-trigger colliders; on contact it stops `CollisionSkin` short and slides along the surface (head-on picks the side toward the target), so round objects are walked around. The command ends when the target is reached or after `PlayerConfig.stuckTimeout` seconds without getting closer. `CurrentTile` is the tile actually containing the player; returned counts are tile changes (sprites are never used for collision; the player's Rigidbody2D is Kinematic so physics never pushes it). `moveTo` steps in a straight line (no pathfinding). Each completed step publishes `PlayerEventBus.OnPlayerMoved` (fog of war reacts to it).

**Map & coordinates:** `TilemapGenerator` builds a Perlin-noise grass/water grid (`TileType[,]`) plus water padding and a fog layer. Biomes: `MapGenerationConfig.biomeConfig` (`BiomeConfig` asset, biomes inline with weight and resource list) → `BiomeMap.Generate` splits the map into noise-warped Voronoi cells, each assigned a weighted-random biome (every biome appears at least once); query with `IMapDataProvider.GetBiome(x, y)`. Use tile indices (`Vector2Int`) for game logic and convert with `TileIndexToWorld` (returns the cell **center**) / `WorldToTileIndex`. Never derive tiles by rounding `transform.position`. Objects use free map positions (`Vector2` in tile units, integers = tile centers): convert with `IMapDataProvider.MapToWorld`, get the containing tile with `MapPosition.ToTile`.

**Objects:** `ObjectGenerator` spawns `ResourceObject` prefabs (via `ObjectPool`, keyed by type) at random free positions (any point inside a walkable tile, at least `minObjectSpacing` apart, outside `spawnClearRadius` of the spawn point), per biome (randomness seeded from `IMapDataProvider.Seed`, so a fixed map seed reproduces objects too): for each `BiomeResource` it spawns `density` objects per 100 land tiles of that biome, calling `SetPosition`; placement uses only the prefab's `Collider2D` footprint (`ObjectFootprint`, computed from Box/Circle/Capsule/Polygon shape since prefab bounds are empty; no collider = a point; sprites are expected to have their pivot at the base) — every tile under it must be land and it must stay `spawnClearRadius` from the player spawn; `ResourceObject.Tile` is derived from `Position`. In Run mode only (`Level` passes `TilemapGenerator.Config`, null in the hub) a guaranteed starter set follows: `MapGenerationConfig.starterResources` ({prefab, count}; defaults stick 4, stone 4, tree 2 — enough for flint → axe → workbench) is topped up per object type (`GetType()`, like the pool key; objects already within `starterMaxRadius` count) in the ring `max(starterMinRadius, spawnClearRadius)`–`starterMaxRadius` (3–5 with vision 6 — `PlayerConfig.visionRadius`, a ±6 tile square — so everything is visible from spawn and stays in sight after walking to one of the items), same placement rules, same seeded random after the normal pass; pure counting/ring math is `StarterResourcePlanner`; rows without a prefab are ignored. `ObjectManager` buckets them by containing tile for radius queries (`GetNearestObjectAt` for point lookups). Lua sees fractional `x`/`y`; `moveTo` accepts them and goes to the containing tile. Hierarchy: `ResourceObject` → `HarvestableResource` (no tool) / `ExtractableResource` (tool required) → concrete types in `Objects/Types`; drop/visuals come from `ResourceVariant`. `FindObjectsCommand.TypeMap` maps Lua type names to these classes — update it when adding a type. Each `ResourceItem` has a `durability`; harvesting costs `ResourceVariant.HarvestEnergyCost` (durability × dropAmount). Two actions, both in `ResourceHarvester`: `harvest([x, y] | obj)` picks up non-tool objects (`HarvestableResource`: sticks, stones, dropped loot) straight into `PlayerInventory`; `mine([x, y] | obj)` (`MineCommand`) works on `ExtractableResource` (tree — axe, boulder — pickaxe, sheep — axe), wears the tool and spawns `ResourceVariant.loot` (falls back to drop × dropAmount) on the ground around the object via each item's `worldPrefab` (items without one go straight to the inventory). `harvest` on a minable object fails with "use mine()". Energy: `harvest` costs only the command call; `mine` additionally spends `ResourceVariant.HarvestEnergyCost` (sum of durability × amount of the loot) — `ResourceHarvester.GetEnergyCost` (also the `durability` field in `findObjects`). `PlayerEnergy`/`PlayerInventory` are plain classes created in `Level`. `PlayerInventory` has `RunModifiers.InventorySlots` fixed slots (filled with `PlayerConfig.startingItems` at run start), each a stack of one `ResourceItem` up to `maxStackSize`; `harvest` fails with "inventory is full" before spending energy if the drop won't fit. `drop(slot | "name", [amount])` (`DropCommand`) removes items by 1-based slot or by name (`ResourceItem.MatchesName`: itemId / display name / asset name, case-insensitive) and, if the item has a `worldPrefab` (a harvestable `ResourceObject` whose variant drops that item), spawns one object per unit around the player via `ObjectManager.Spawn` so it can be picked up with `harvest` (costs the item durability like any harvest); items without one (tools, structures) disappear. Objects with a `RequiredTool` (tree, sheep — axe; boulder — pickaxe, drops 3 stones) need a `ToolItem` of that `toolType` in the inventory: `ResourceHarvester` picks the most worn working one (`PlayerInventory.FindToolSlot`) and wears it by `wearPerUse` per harvest; at 0 durability it breaks and disappears. Tools never stack — each slot keeps its own durability (`InventorySlot.Durability`, shown as a bar on the inventory panel). Lua can read state via `findObjects([type])` (no argument = every object in sight plus visible enemies; `gold_ore` = `GoldOreObject`, pickaxe; Lua type names are snake_case of the class name without `Object` — `LuaObjectList.GetTypeName`) — it returns a `LuaObjectList`: array of plain object tables (`id`, `kind` = "object", `x`, `y`, `type`, `durability`, `distance`, `tool`; enemy entries — see Threat section) plus `count` and colon-methods (`getNear/getFar/getMin/getMax/getRandom/getAt/find`, chainable `where/sortBy/take` that build a new list, `contains/indexOf/sum`; each call costs `LuaObjectList.MethodCost`; harvested objects are skipped; `LuaObjectList.Methods` feeds help, highlighting, completion and line costs), `check(x, y | obj | "direction", [distance])` (`CheckCommand`: one tile — `type` summary, `terrain`, `walkable`, `biome`, `structure` via `StructureManager.GetStructureAt`, `player`, `objects` as a `LuaObjectList` from `ObjectManager.GetObjectsAtTile`, `enemies` as a `LuaObjectList` from `EnemyManager.GetEnemiesAtTile` (`type` summary: structure, else enemy `TypeId`, else first object, else water/empty); only tiles with no fog at all — `IFogProvider.IsVisible`, implemented by `FogOfWarSystem` — otherwise `nil, reason`) and `getInventory()` (slots with `name`, `count`, tool `durability`/`maxDurability`; result has `count` and `free`).

**Crafting:** recipes are `[Serializable] CraftRecipe` entries (result + `ingredients` + `CraftingStation` + `energyCost`) edited inline in the single `RecipeBook` asset (`ScriptableObjects/Recipes/RecipeBook.asset`, assigned on `Level`); `Scripts/Editor/CraftingDrawers.cs` draws them as cards with sprite previews and edits the result item's name/sprite in place. Icons everywhere come from `ResourceItem.Icon`: the sprite of `iconPrefab`, else of `worldPrefab` (first `SpriteRenderer` with a sprite, children included; `StructureItem` defaults to its structure prefab), falling back to the static `sprite` only for items without a prefab — never read `.sprite` directly in UI. `craft("name")` (`CraftCommand`) finds the recipe by result display name/itemId (case-insensitive), checks ingredients/energy, and swaps ingredients for the result atomically via `PlayerInventory.TryExchange`. Always go through `CraftRecipe.GetRequirements()` (skips empty rows, merges duplicate items) — `craft()`, the panel, and the inspector drawer all use it; `CanCraft` is what the panel highlights. A recipe with a `station` needs a placed `Structure` of that station within `PlayerConfig.structureInteractionRadius` of the player (`IStationProvider`, implemented by `StructureManager`); `CanCraft(getCount, stationNearby)` and the panel (re-checked every 0.5 s while open) use the same rule. `CraftingPanel` (bottom-right button + right side panel) only displays recipes; crafting is code-only.

**Structures:** a `StructureItem` (inventory item) references a `Structure` prefab (MonoBehaviour with a `CraftingStation`, pivot at the base, `Collider2D` footprint, auto `DepthSortedSprite`). `build("name", [x, y])` (`BuildCommand`) places it from the inventory: without coordinates it tries the 8 neighbouring tiles, with coordinates the point must be within reach; `StructureManager` (plain class created in `Level`, instances live under a runtime "Structures" GameObject) requires land under the footprint and no overlapping non-trigger collider (the player included), then calls `Physics2D.SyncTransforms` so movement sees the new collider. Assets: `Prefabs/Structures/Workbench.prefab`, `ScriptableObjects/Items/Workbench.asset`. `CraftingStation` is serialized as a number — append new values at the end only (`Campfire` is last; the campfire is a plain `Structure` with that station).

**Food:** `FoodItem : ResourceItem` (`energyRestore`, `healthRestore`; not a material) comes from `berry_bush` (`BerryBushObject`, harvest) and `sheep` (`SheepObject`, mine with an axe, static). `eat(slot | "name")` (`EatCommand`, cost 1, in the starting set) finds a `FoodItem` (1-based slot or `MatchesName`), restores via `PlayerEnergy.Restore` (capped at max, does **not** reduce `TotalSpent`, unlike `Refund`) and `PlayerHealth.Heal` (returns the healed amount); if nothing would be restored it returns `nil, "already full"` without consuming the item (the call's own fee does not count as room for energy), otherwise removes one and returns `true, energy, health` (amounts restored) and publishes `FoodEaten` (Id = `MetaProgress.GetItemKey`). `getInventory()` adds `food = true`, `energy`, `health` for food slots.

**Puzzles (stage 6, `Scripts/Puzzles`, spec — GameDesign §10.4):** `PuzzleConfig` SO on `Level` (null = warning, no puzzles): obelisk/wall/chest prefabs, `crystalItem`, counts, distances, reward amounts. Type ids `PuzzleTypes.CodeTask`/`Maze` (`"code_task"`/`"maze"`) are the map-event ids — `Level` calls `UnlockRegistry.SetKnownMapEvents(PuzzleTypes.All)` in both modes. `PuzzleManager` (plain, `IDisposable`, created in `Level` after enemies and before `LuaSandbox`, exposed as `Level.Puzzles`, empty in the hub, disposed in `Level.OnDestroy`) holds the puzzles: `GetById`, `GetPuzzleAt(tile)`, `GetPuzzlesInRadius(point, r, typeId)`, `IsMazeWall(tile)`, `IsInReach` (player `Position` within `PlayerConfig.structureInteractionRadius` of the area edge), `TrySolveCodeTask(puzzle, answer)` → `PuzzleSolveResult` (`Describe` gives the Lua error text). `PuzzleGenerator.Generate` (run only, unlocked types only via `IsMapEventUnlocked`, deterministic from `Seed`; maze first, then obelisks) needs land with a 1-tile margin, fully in fog, ≥ `minDistanceFromCamps` from `EnemyManager.CampCenters`, spawn/spacing distances from the config; map objects under the area are removed (`ObjectManager.RemoveObjectsInArea` → `ResourceObject.Despawn`, no events). Base `PuzzleStructure` (MonoBehaviour: `Id`, `TypeId`, `Position`, `Bounds`, `IsSolved` for this run). `CodeTaskPuzzle` (obelisk, auto `DepthSortedSprite`): kind `sum`/`max`/`count` (2 obelisks = 2 different kinds), `GetTask()` → `CodeTask` {`KindId`, `Text`, `Input` (12 ints), `Limit`, `Answer`} regenerated per code run (`CodeTaskSource` keyed by `GameEventBus.ActiveRunId`, so the answer must be computed in the same run). Rewards (`PuzzleRewards`, until the run ends, through `RunModifiers.AddEnergyLimit/AddMaxHealth/DelayThreat`): sum — `BaseEnergyLimit` +10 and +10 energy now; max — `MaxHealth` +20 and full heal (`PlayerHealth.SetMax`); count — threat +1 day if not started, else as sum. `MazePuzzle`: 7×7 `MazeLayout` (perfect 3×3-cell maze, recursive backtracker, one entrance in the middle of a random side, retried until the path to the centre is ≥ `mazeMinPathLength`), walls are `mazeWallPrefab` instances with colliders (movement stops on them via `Collider2D.Cast`; the tiles stay `IsWalkable`, so Lua `check` must ask `IsMazeWall`), chest at the centre (its solid colliders are switched to triggers). `FogOfWarSystem.AddHedgeArea(inner 5×5, mazeVisionRadius)`: inside, fog lifts only within radius 1 of the player. Player steps on the centre tile (`PlayerEventBus.OnPlayerMoved`) → solved, `crystal` ×2 into the inventory (overflow on the ground via `worldPrefab`). Every solve: `MarkSolved` → reward → `GameEventBus` `PuzzleSolved` (Id = type, Tag = task kind) → notification → `OnPuzzleSolved`. Lua side: `LuaSandbox.Initialize(..., puzzles)` (optional, null in tests). `puzzle([obj | x, y])` (`PuzzleCommand`, 1; no args — nearest in reach) → `{kind, text, input, limit, solved, id, type}` (maze: kind `"maze"`, empty input) and `solve(obj, answer)` (`SolveCommand`, 2) → `true` / `nil, reason` (`PuzzleManager.Describe`); both need `IsInReach`, are not in the starting set (`hub_builder` reward). Helpers in `LuaPuzzles` (type names `obelisk`/`maze`, fog visibility = any tile of the area visible, argument resolving, harvest/mine/attack refusal texts). `findObjects` types `obelisk`/`code_task`, `maze`, `puzzle` (all), also included in `findObjects()`: entries `kind = "puzzle"`, id = `LuaObjectList.PuzzleIdOffset` (2·10⁹) + `Id`, `x`/`y` = `Position` (maze — centre), `solved`, `distance` (to the area edge from `Executor.Position`), maze `entranceX/Y` = `ApproachTile`. `check`: maze wall → `type`/`structure` `"wall"`, `walkable = false`; maze centre → `"chest"`; obelisk → `"obelisk"`; `puzzle` field = the puzzle table. `EnergyCounter` does not charge identifiers after `.`/`:` that match a command name (`info.puzzle`), as nothing is charged at runtime. Tests: `PuzzleCommandTests`.

**UI:** `CodeEditorManager` (on the `UIDocument`) creates a `window-layer` (code windows live there, below everything else), the `TopBar` (its Help button opens `CommandHelp`, built from the command registry + `EnergyConfig`, ready-made commands grouped via `ILuaCommand.IsReadyMade`), the bottom `InventoryBar`, the `CraftingPanel` (slots rendered from `UIEventBus.OnInventoryChanged` snapshots), the main window, and auxiliary "class" windows from UXML templates in `Scripts/UI/GUI`. `CodeLibraryPanel` (hidden drawer, opened by a small tab at the middle of the right edge; opening it closes `CraftingPanel` and vice versa) is the code library: dropping an auxiliary window (not Main) by its header onto the open panel or the tab saves `Title` + `Code` through `CodeLibrary` to `Application.persistentDataPath/code_library.json` (same title overwrites) and snaps the window back; entries can be reopened as auxiliary windows (title made unique) or deleted (two clicks). Drop detection is in `CodeEditorManager` via `WindowDragger.OnDragMoved/OnDragEnded`. Windows extend `CodeEditorWindowBase` (a `VisualElement`) composed of helpers in `UI/Elements` (`CodeEditor`, `WindowDragger`, `WindowResizer`, `TitleEditor`). Keyboard input is swallowed by the UI container unless a code field was focused by mouse click (`PlayerEventBus.OnUIFocused`). UI Toolkit keyboard navigation (WASD/arrows/Tab/Enter, the same keys as camera movement) is blocked at the panel root in `CodeEditorManager.BlockKeyboardNavigation` via `focusController.IgnoreEvent`. `CodeEditorManager` also implements `IPointerOverUIProvider` (`panel.Pick` at the cursor, ignoring full-screen backgrounds); `CameraController` uses it so mouse-wheel zoom (orthographic size, clamped `minZoom`–`maxZoom`) does not fire over windows or panels. Achievements UI (`CodeEditorManager` gets `Level.AchievementTracker` in `Initialize`): `RunScreens.uxml` embeds three templates above the screens (`<ui:Template>`/`<ui:Instance>`, no scene fields needed; hosts from `RunScreens.GetOverlay`, stretched and picking-ignored) — `AchievementsPanel` (modal list: icon, title, description, progress bar, EfficientGather goal + current run, rewards; opened by the TopBar Achievements button and the hub button; rebuilt on tracker events only while open, otherwise marked dirty), `UnlockPopup` (modal "Unlocked: X" on `UnlockRegistry.OnUnlocked`, queued and suspended while code runs, shown the frame after the run ends; command — `ILuaCommand` signature/description/cost from `LuaSandbox.AllCommands`, construct — explanation + highlighted example from the static `LuaConstructGuide` + cost from `EnergyConfig`, recipe — `ResourceItem.Icon` + ingredients, hub building/map event — one line) and `AchievementToasts` (self-hiding queued toast on `OnAchievementCompleted`, click to dismiss). Texts: `AchievementText` (English rewards via `AchievementReward.Describe()`); the run summary lists `RunSummary.Achievements`. Tutorial & hints (stage 5): a fourth template `TutorialOverlay.uxml` sits above all overlays in `RunScreens.uxml`; `TutorialOverlay` (view) draws one non-modal card + pulsing frame + diamond arrow around a target element, repositioned every tick from its `worldBound` (only the card is pickable, buttons `focusable = false`); `TutorialController` (plain class created by `CodeEditorManager.CreateTutorial`, disposed in its `OnDestroy`, started one panel update after `Initialize` with Hub/Run from `RunScreens.IsHubShown`) runs the steps of `TutorialSteps.Steps` (GameDesign §10.5: anchor `TutorialAnchor` resolved by `CodeEditorManager.FindTutorialAnchor`, text with `code` in backticks highlighted, `After`/`Requires`/`Done`/`Skip` predicates over `TutorialState`; the current step is the first not-done one whose `After` and `Requires` hold, so list order = priority; a step whose `Done` already holds is completed ahead of time; `Done == null` → Next button) and the concept hints of `TutorialSteps.Concepts` (call, arguments, variable, condition, loop, function — on first use in code, tokenized with `LuaTokenizer`; loops/functions short since `UnlockPopup` explains them; a step with `CoversConcept` marks it shown). Conditions are facts (`TutorialFacts`) from `GameEventBus` (Crafted, Mined, ConstructUsed, EnemyFound, run start/finish) and UI notifications from `CodeEditorManager` (`Notify`: Help/crafting/library/achievements opened, Start Run, window saved), plus code text (`SetCode` on every code change). Cards wait while code runs (except `ShowWhileRunning`) and hide while a modal (`UnlockPopup`, `AchievementsPanel`, exit confirm, summary) is open. Persistence in `MetaProgress`: `tutorialFlags` `step:<id>`, `concept:<id>`, `skipped` and `HintsEnabled` (saved immediately); Hints toggle in the TopBar and the hub card, Reset tutorial (two clicks) in the hub. Camp UI (stage 4): `CodeEditorManager.Initialize` gets `Level.HubService`/`HubPlacement` (null in a run, `IsHub`); in the camp code does not run — the window layer, `TopBar`, `InventoryBar`, `CraftingPanel` and `CodeLibraryPanel` are hidden (`display: none`) and Run is refused. `RunScreens.uxml` embeds `HubPanel.uxml` as `hub-screen` (`<ui:Instance>`, picking-ignored like its root and the bottom hint row, so only the two panels count as "over UI" and clicks/zoom on the grid reach `HubPlacementController`/`CameraController`): left — stats, material stock (`RunScreens.RefreshHub`, icons via `HubIconResolver` from building costs), Achievements, Start Run, Hints, Reset tutorial; right — `HubBuildPanel` (cards of `HubService.Definitions`: `Icon`, title, size, description, `DescribeEffects`, cost chips `Item.Icon` + have/need, state Locked "Unlock: <achievement>" (found by a `HubBuilding` reward in `AchievementTracker.Definitions`) / Built / Not enough materials; Build → `HubPlacement.Begin`, the same button turns into Cancel; while placing a bottom hint "Click a cell to build · Right click / Esc to cancel" and the tutorial card is hidden). Rebuilt on `HubService.OnBuilt` (also refreshes the stock), placement `OnPlaced`/`OnCancelled`/`OnFailed` and `OnUnlocked(HubBuilding)`. Notifications: `UIManager.SetNotificationDisplay(INotificationDisplay)` — in the camp `HubBuildPanel` shows the last `UIEventBus` notification under the hint for 4 s (refusal reasons from `HubPlacementController`, "X built"); in a run they are only logged. Hub tutorial step `hub_build` (anchor `HubBuildPanel`, only while something is buildable — `TutorialState.HubBuildAvailable`; done by `TutorialFacts.HubBuilt` from `GameEventBus` `HubBuildingBuilt` or an existing building). Run log & error hints: the main window has a `RunLog` strip at the bottom (`RunLog.uss`; hidden while empty, × clears, cleared on every Run) — in a run it is `UIManager`'s notification display, and failed runs go through `UIEventBus.OnCodeErrorReported(LuaErrorExplanation)` (published by `CodeEditorManager`): raw `ErrorMessage` plus, when Hints are on, "Line N in Main", a plain-English explanation and "Try: …" from the static `LuaErrorExplainer` (regex table over the real Lua-CSharp/`EnergyMeter`/`LuaConstructGuard`/command texts; aux-window lines are shifted by the `function Title(...)` wrapper line; Lua-CSharp prints expected keywords as token chars 256+, decoded; "Did you mean" by Damerau-Levenshtein over registry commands, `LuaObjectList.Methods`, window titles, the `known:` list of `findObjects`), and the error line number is coloured in that window's gutter until the code changes. Keep its regexes in sync when changing error texts (EditMode tests in `LuaErrorExplainerTests`). The UI is mouse-only, and code fields reject any focus that didn't start with a `PointerDown`. Keep it that way, otherwise camera keys can move focus into a code field and overwrite the code.

**Localization (RU/EN, `Scripts/Localization`, GameDesign §11):** the source language is English — UI strings stay in code, UXML and assets as-is; Russian is a table "English → Russian" (`LocTablesRu.Sections`: `LocRuUi`, `LocRuCommands`, `LocRuContent`, each a static class with `public static readonly (string En, string Ru)[] Entries`). `Loc.T("text")` / `Loc.F("Day {0}", day)` return the translation for `Loc.Language` (no translation → English, editor warns once); static UXML texts are translated by `LocUxml`. **Every new user-facing string must go through `Loc` and get a row in a table** (EditMode tests `LocalizationTests`/`LocCommandsTests` check coverage and format placeholders). The Lua API is never translated: command names, signatures, object type names, table fields and error strings returned to Lua are identical in both languages, since players compare them in code (exception: `puzzle().text` — a human-readable task description nobody compares, translated via `Loc.T` in `LuaPuzzles`); help, command descriptions, hints, achievements and unlock popups are translated. The language lives in `MetaProgress.Language` (survives `ResetAll`; first launch — by system language), is switched in the camp and applied by a scene reload; `Loc.OnLanguageChanged` is static — unsubscribe in `OnDestroy`.

**Code editor internals** (`UI/Elements/CodeEditor.cs`): shared services (theme, `LuaSyntaxHighlighter`, `LuaCompletionProvider`, line-cost function) are built once in `CodeEditorManager.CreateContext()` and passed to every window as `CodeEditorContext`. Highlighting is a rich-text `Label` inserted into the `TextField`'s own `ScrollView` content container, under the field's text, which is made transparent (caret/selection colors live in `CodeEditorCommon.uss`). The highlighted text must stay character-for-character identical to the source, which is why `<` is wrapped in `<noparse>`. Line-number and line-cost gutters are aligned to the text element's `worldBound` (which already includes scroll). Command names, signatures, descriptions, and costs for highlighting/completion come from the `ILuaCommand` registry — new commands show up automatically. Quirk: after setting `TextField.value` from code, the field applies `SelectRange` only several frames later, so `CodeEditor` tracks `_pendingCursor` and reads the cursor through `CursorIndex`. Use `ReplaceRange`/`InsertText` for programmatic edits.

## Conventions

- Code comments are in Russian; save `.cs` files as **UTF-8 with BOM** (some were previously CP1251 and showed mojibake).
- Style: `[SerializeField] private` fields, `_camelCase` private members, `Debug.Assert` reference validation in a `ValidateReferences()` method, section separators like `// ─── Public API ───`.
- Classes are in the global namespace.

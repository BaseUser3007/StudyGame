# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Unity **6000.4.10f1** 2D (URP) programming game (working title "CodeRogue" in `CreateAssetMenu` paths). The player doesn't control the pawn directly — they write **Lua** in in-game editor windows, and Lua calls C# commands that move the pawn, query objects, etc. Every Lua construct costs "energy". Art comes from the third-party `Assets/Tiny Swords` pack — don't modify it. All project code lives in `Assets/_Game`; the only scene in the build is `Assets/_Game/Scenes/Game/SampleScene.unity`.

**Target design & plan:** `Docs/GameDesign.md` (agreed vision of the final game: roguelike runs ↔ hub, world threat, achievements unlocking commands/language constructs, tutorial, puzzle structures — plus open questions) and `Docs/Roadmap.md` (staged checklist, ★ = scope for the 2026-10-26 slice). Check new features against them and tick off Roadmap items when done.

Key dependencies: Lua-CSharp 0.5.5 (`Lua`, `Lua.Standard` namespaces; DLLs installed by NuGetForUnity into `Assets/Packages`, Unity glue via the `com.nuskey8.lua.unity` UPM package), UniTask, UI Toolkit (UXML/USS, no uGUI), Input System, Tilemap + Rule Tiles. Binary assets (png, dll) are in Git LFS.

## Build / verify

There are no tests, asmdefs, or lint setup. All game code compiles into `Assembly-CSharp`.

- Fast compile check without opening Unity (uses the Unity-generated, gitignored csproj):
  `dotnet build Assembly-CSharp.csproj -nologo -v q`
  The csproj lists files explicitly and is only regenerated by Unity — a **newly added** `.cs` file won't be compiled by this command until Unity regenerates the project (or you add a `<Compile Include>` line locally).
- Real verification requires Play Mode in the Unity editor.

## Architecture

**Composition root:** `Core/Level.cs` holds serialized references to every system and wires them in `Awake` in a fixed order: map generation → spawn point → player instantiate → `PlayerCommandExecutor` → fog of war → camera → objects → run state (`RunModifiers`, `PlayerEnergy`, `PlayerHealth`, `PlayerInventory`) → structures → `DayCycle` → `LuaSandbox` → UI → `RunController`. Systems don't find each other; dependencies are passed via `Initialize(...)` methods, mostly as interfaces (`IMapDataProvider` implemented by `TilemapGenerator`, `IPlayerDataProvider` implemented by `PlayerConfig`). When adding a system, add a serialized field + assert + an `Initialize` call here.

**Events:** two static buses — `PlayerEventBus` (player moved, UI focus, camera, day start/end) and `UIEventBus` (energy, per-window code cost, inventory, notifications). `UIManager` is the single subscriber that pushes `UIEventBus` changes into UI elements. Because the buses are static, always unsubscribe in `OnDestroy` with named methods (not lambdas).

**Config:** tunables are ScriptableObjects in `Assets/_Game/ScriptableObjects` (`PlayerConfig`, `EnergyConfig`, `MapGenerationConfig`, `CodeEditorTheme`, `ResourceVariant`s).

**Lua pipeline** (`Scripts/Lua`):
- A command = class deriving from `LuaCommandBase` (or `PlayerCommandBase`, which adds `Executor` and `MapData`). It declares `Name`, `EnergyCost`, `Signature`, `Description` and overrides `ExecuteAsync(context, ct)` (return the number of values passed to `context.Return`). The base `Register(state, meter)` charges `EnergyCost` through `EnergyMeter` on **every call**, then runs `ExecuteAsync`. No command may be free: `EnergyCost` must be > 0 (asserted on registration); functions a command hands back to Lua (e.g. `getNear` on the `findObjects` result) charge through the protected `Meter` too. Pass `ct` into any awaited executor call so Stop/cancellation works.
- New commands must be registered in `LuaSandbox.RegisterCommands()` (via `AddCommand`).
- Design rule: basic commands are cheap; convenience ("ready-made") commands such as `obtain([type])` do what a short snippet of basic commands does but cost more than that snippet, so writing your own code saves energy. They must reuse the same services (e.g. `ResourceHarvester`) so physical costs are identical.
- `LuaSandbox.ExecuteAsync`: auxiliary editor windows are wrapped as global functions `function <WindowTitle>(...) <code> end` (so window titles must be valid Lua identifiers — enforced by `LuaIdentifierValidator` in `TitleEditor`), then the main window code runs. Execution is cancellable (`Stop()`, the Run button toggles to Stop) and guarded by a thread-pool watchdog that cancels if the main thread is blocked longer than `freezeTimeoutSeconds` (catches infinite loops without awaits).
- Energy is spent at **runtime**, for what actually executes; nothing is charged on Run. `EnergyInstrumenter` rewrites each chunk before execution (no newlines added, so line numbers stay): `if/elseif/while/until` → `kw __energy(c) and cond` (every condition check), `for … do` → `do ;__energy(c);` (every iteration), `function f(…)` → charge on every call, `local`/`return`/`else` → charge per execution. Costs come from `EnergyConfig`. `__energy` and command calls go through `EnergyMeter`; when energy runs out it throws, stays exhausted (so `pcall` can't swallow it) and cancels the run with an "out of energy" result. Syntax is checked on the original code first (`LuaState.Load`) so compile errors point at the player's code; chunks are named `Main` / window title. The tokenizer handles `--[[ ]]` / `[[ ]]` long brackets — keep it exact (the instrumenter refuses to rewrite code it can't re-assemble).
- `EnergyCounter` computes the same costs statically per line/window for display: it's the price of one pass, loops multiply it. Physical actions (harvest durability, craft energy) are charged separately by their services.
- Unlocks: `UnlockRegistry` (plain class created in `Level` from the `UnlockConfig` asset `DefaultUnlockConfig` + `MetaProgress`): unlocked = starting set ∪ saved (`unlockAll`/missing config = all; `unlockAll` stays on until stage 2 achievements can grant unlocks). `UnlockCommand`/`UnlockConstruct` reject unknown names, save immediately and raise `OnUnlocked(UnlockKind, id)` on first unlock. `LuaSandbox` keeps all commands in `AllCommands` but only unlocked ones in `Registry` (help/highlight/completion/EnergyCounter never see locked ones); locked commands get a Lua stub erroring "command `x` is not unlocked yet" (no energy). Unlocks during a run apply after it ends, then `OnUnlocksApplied` fires and `CodeEditorManager` rebuilds help, highlighter API names, line costs and class-window availability. Construct ids in `LuaConstructs` (`local`, `if`+elseif/else, `for`, `while`, `repeat`+until, `function`, `classes` = auxiliary windows); `goto` and `::labels::` are forbidden permanently (they'd be free loops); break/return/and/or/not/do are never locked. After the syntax check of all windows and before instrumenting, `LuaConstructGuard` scans each window's original code by tokens and refuses with e.g. "loop `for` is not unlocked yet (Main, line 3)"; aux windows with code while `classes` is locked are refused. No energy is spent, but the refusal counts as a day run, like a compile error (intended). Locked keywords are drawn with `CodeEditorTheme.lockedKeywordColor`.
- The sandbox strips `load`, `loadfile`, `dofile`, `require`, `package`, `io`, `debug`, `collectgarbage` after `OpenStandardLibraries()` and leaves only `os.clock/time/date` — loading code from strings would bypass the guard and the energy instrumenter. `LuaModuleLoader` exists but is not wired in.

**Hub ↔ run & meta progress:** `GameSession` (static) keeps the requested `GameMode` (Hub/Run) and the lazily loaded `MetaProgress` across scene loads (statics are reset in `SubsystemRegistration` for Play Mode without domain reload). Every transition reloads the scene (`GameSession.StartRun`/`ReturnToHub`), so each run starts clean with a new random seed; the first load uses `Level.startInHub`. The hub is for now a full-screen UI screen (`RunScreens`: hub with the material stock + Start Run, exit confirmation, run summary) over the generated map; the real hub location with a grid is Roadmap stage 4. `RunController` (plain class created last in `Level`) handles the TopBar Exit Run button (not while code runs; confirmation inside the UI) and `PlayerHealth.OnDied` (stops the code): it builds a `RunSummary`, moves only items with `ResourceItem.IsMaterial` (`MaterialResource`) to the hub stock — nothing on defeat — and saves `MetaProgress` immediately, before the summary is shown. `MetaProgress` (`meta_progress.json` in `persistentDataPath`, written only by `Save()`) stores unlocked commands/constructs, achievements, events, tutorial flags, hint setting, hub material stock (keyed by `itemId`, else asset name) and hub buildings; `JsonFileStore` does the atomic write / `.bak` on a broken file for it and `CodeLibrary`. `RunModifiers.Create(PlayerConfig, MetaProgress)` holds per-run values (base energy limit, max health, inventory slots, runs per day, threat day, starting items) — run systems read these, not `PlayerConfig`; hub buildings will add their bonuses there. `PlayerHealth` (plain class, `UIEventBus.OnPlayerHealthChanged` → TopBar bar, `health`/`maxHealth` in `getStatus()`) has no damage source yet (enemies, stage 3).

**Day cycle & energy budget:** `DayCycle` (plain class created in `Level`, attached to `LuaSandbox.OnRunningChanged`) gives `RunModifiers.RunsPerDay` (3) runs per day — every finished run counts, errors and Stop included; after the last one (or the End Day button, not while running) the day ends: `PlayerEnergy.SetMax(max, refill)` with max = `RunModifiers.BaseEnergyLimit` − penalty (`base × energyPenaltyMultiplier` if the day ended with < 1 energy, next day only) + bonus (`homeBonusPerDay` × consecutive nights ended near a `Structure` with `isSleepingPlace`, capped at `maxEnergyBonus`), clamped to `minEnergyLimit`. State goes to the top bar through `UIEventBus.OnDayChanged(DayInfo)`; Lua reads it with `getStatus()`. Energy is the per-day budget: language constructs are cheap (`EnergyConfig`: loop iteration/check 1, `if` 0.5, `local`/`return`/`else`/function call 0), world actions are the main sink. Food (later) is meant to add energy.

**Depth sorting:** `DepthSortedSprite` sets `sortingOrder` of all child `SpriteRenderer`s from `transform.position.y` via `DepthSorting` (bottom of map = 1000, top = 100; range configured in `Level` right after map generation). `ResourceObject` adds it automatically and refreshes on `SetPosition`; the player gets it in `Level.SpawnPlayer` with `Dynamic = true`. The fog tilemap is forced to `DepthSorting.OverlayOrder` (2000) so it stays above all objects — keep any new world sprites inside 100–1000 and overlays above.

**Player movement:** `PlayerCommandExecutor` keeps the logical `CurrentTile` and animates tile-by-tile with UniTask; walkability comes from `IMapDataProvider`, and movement is continuous (`MoveTowardsAsync`): the target is the last land tile on the straight line (water stops immediately), and each frame the player's own non-trigger `Collider2D` is cast (`Collider2D.Cast`, its real feet shape) against other non-trigger colliders; on contact it stops `CollisionSkin` short and slides along the surface (head-on picks the side toward the target), so round objects are walked around. The command ends when the target is reached or after `PlayerConfig.stuckTimeout` seconds without getting closer. `CurrentTile` is the tile actually containing the player; returned counts are tile changes (sprites are never used for collision; the player's Rigidbody2D is Kinematic so physics never pushes it). `moveTo` steps in a straight line (no pathfinding). Each completed step publishes `PlayerEventBus.OnPlayerMoved` (fog of war reacts to it).

**Map & coordinates:** `TilemapGenerator` builds a Perlin-noise grass/water grid (`TileType[,]`) plus water padding and a fog layer. Biomes: `MapGenerationConfig.biomeConfig` (`BiomeConfig` asset, biomes inline with weight and resource list) → `BiomeMap.Generate` splits the map into noise-warped Voronoi cells, each assigned a weighted-random biome (every biome appears at least once); query with `IMapDataProvider.GetBiome(x, y)`. Use tile indices (`Vector2Int`) for game logic and convert with `TileIndexToWorld` (returns the cell **center**) / `WorldToTileIndex`. Never derive tiles by rounding `transform.position`. Objects use free map positions (`Vector2` in tile units, integers = tile centers): convert with `IMapDataProvider.MapToWorld`, get the containing tile with `MapPosition.ToTile`.

**Objects:** `ObjectGenerator` spawns `ResourceObject` prefabs (via `ObjectPool`, keyed by type) at random free positions (any point inside a walkable tile, at least `minObjectSpacing` apart, outside `spawnClearRadius` of the spawn point), per biome (randomness seeded from `IMapDataProvider.Seed`, so a fixed map seed reproduces objects too): for each `BiomeResource` it spawns `density` objects per 100 land tiles of that biome, calling `SetPosition`; placement uses only the prefab's `Collider2D` footprint (`ObjectFootprint`, computed from Box/Circle/Capsule/Polygon shape since prefab bounds are empty; no collider = a point; sprites are expected to have their pivot at the base) — every tile under it must be land and it must stay `spawnClearRadius` from the player spawn; `ResourceObject.Tile` is derived from `Position`. `ObjectManager` buckets them by containing tile for radius queries (`GetNearestObjectAt` for point lookups). Lua sees fractional `x`/`y`; `moveTo` accepts them and goes to the containing tile. Hierarchy: `ResourceObject` → `HarvestableResource` (no tool) / `ExtractableResource` (tool required) → concrete types in `Objects/Types`; drop/visuals come from `ResourceVariant`. `FindObjectsCommand.TypeMap` maps Lua type names to these classes — update it when adding a type. Each `ResourceItem` has a `durability`; harvesting costs `ResourceVariant.HarvestEnergyCost` (durability × dropAmount). Two actions, both in `ResourceHarvester`: `harvest([x, y] | obj)` picks up non-tool objects (`HarvestableResource`: sticks, stones, dropped loot) straight into `PlayerInventory`; `mine([x, y] | obj)` (`MineCommand`) works on `ExtractableResource` (tree — axe, boulder — pickaxe, rabbit), wears the tool and spawns `ResourceVariant.loot` (falls back to drop × dropAmount) on the ground around the object via each item's `worldPrefab` (items without one go straight to the inventory). `harvest` on a minable object fails with "use mine()". Energy: `harvest` costs only the command call; `mine` additionally spends `ResourceVariant.HarvestEnergyCost` (sum of durability × amount of the loot) — `ResourceHarvester.GetEnergyCost` (also the `durability` field in `findObjects`). `PlayerEnergy`/`PlayerInventory` are plain classes created in `Level`. `PlayerInventory` has `RunModifiers.InventorySlots` fixed slots (filled with `PlayerConfig.startingItems` at run start), each a stack of one `ResourceItem` up to `maxStackSize`; `harvest` fails with "inventory is full" before spending energy if the drop won't fit. `drop(slot | "name", [amount])` (`DropCommand`) removes items by 1-based slot or by name (`ResourceItem.MatchesName`: itemId / display name / asset name, case-insensitive) and, if the item has a `worldPrefab` (a harvestable `ResourceObject` whose variant drops that item), spawns one object per unit around the player via `ObjectManager.Spawn` so it can be picked up with `harvest` (costs the item durability like any harvest); items without one (tools, structures) disappear. Objects with a `RequiredTool` (tree, rabbit — axe; boulder — pickaxe, drops 3 stones) need a `ToolItem` of that `toolType` in the inventory: `ResourceHarvester` picks the most worn working one (`PlayerInventory.FindToolSlot`) and wears it by `wearPerUse` per harvest; at 0 durability it breaks and disappears. Tools never stack — each slot keeps its own durability (`InventorySlot.Durability`, shown as a bar on the inventory panel). Lua can read state via `findObjects` — it returns a `LuaObjectList`: array of plain object tables (`id`, `x`, `y`, `type`, `durability`, `distance`, `tool`) plus `count` and colon-methods (`getNear/getFar/getMin/getMax/getRandom/getAt/find`, chainable `where/sortBy/take` that build a new list, `contains/indexOf/sum`; each call costs `LuaObjectList.MethodCost`; harvested objects are skipped; `LuaObjectList.Methods` feeds help, highlighting, completion and line costs), `check(x, y | obj | "direction", [distance])` (`CheckCommand`: one tile — `type` summary, `terrain`, `walkable`, `biome`, `structure` via `StructureManager.GetStructureAt`, `player`, `objects` as a `LuaObjectList` from `ObjectManager.GetObjectsAtTile`; only tiles with no fog at all — `IFogProvider.IsVisible`, implemented by `FogOfWarSystem` — otherwise `nil, reason`) and `getInventory()` (slots with `name`, `count`, tool `durability`/`maxDurability`; result has `count` and `free`).

**Crafting:** recipes are `[Serializable] CraftRecipe` entries (result + `ingredients` + `CraftingStation` + `energyCost`) edited inline in the single `RecipeBook` asset (`ScriptableObjects/Recipes/RecipeBook.asset`, assigned on `Level`); `Scripts/Editor/CraftingDrawers.cs` draws them as cards with sprite previews and edits the result item's name/sprite in place. Icons everywhere come from `ResourceItem.Icon`: the sprite of `iconPrefab`, else of `worldPrefab` (first `SpriteRenderer` with a sprite, children included; `StructureItem` defaults to its structure prefab), falling back to the static `sprite` only for items without a prefab — never read `.sprite` directly in UI. `craft("name")` (`CraftCommand`) finds the recipe by result display name/itemId (case-insensitive), checks ingredients/energy, and swaps ingredients for the result atomically via `PlayerInventory.TryExchange`. Always go through `CraftRecipe.GetRequirements()` (skips empty rows, merges duplicate items) — `craft()`, the panel, and the inspector drawer all use it; `CanCraft` is what the panel highlights. A recipe with a `station` needs a placed `Structure` of that station within `PlayerConfig.structureInteractionRadius` of the player (`IStationProvider`, implemented by `StructureManager`); `CanCraft(getCount, stationNearby)` and the panel (re-checked every 0.5 s while open) use the same rule. `CraftingPanel` (bottom-right button + right side panel) only displays recipes; crafting is code-only.

**Structures:** a `StructureItem` (inventory item) references a `Structure` prefab (MonoBehaviour with a `CraftingStation`, pivot at the base, `Collider2D` footprint, auto `DepthSortedSprite`). `build("name", [x, y])` (`BuildCommand`) places it from the inventory: without coordinates it tries the 8 neighbouring tiles, with coordinates the point must be within reach; `StructureManager` (plain class created in `Level`, instances live under a runtime "Structures" GameObject) requires land under the footprint and no overlapping non-trigger collider (the player included), then calls `Physics2D.SyncTransforms` so movement sees the new collider. Assets: `Prefabs/Structures/Workbench.prefab`, `ScriptableObjects/Items/Workbench.asset`.

**UI:** `CodeEditorManager` (on the `UIDocument`) creates a `window-layer` (code windows live there, below everything else), the `TopBar` (its Help button opens `CommandHelp`, built from the command registry + `EnergyConfig`, ready-made commands grouped via `ILuaCommand.IsReadyMade`), the bottom `InventoryBar`, the `CraftingPanel` (slots rendered from `UIEventBus.OnInventoryChanged` snapshots), the main window, and auxiliary "class" windows from UXML templates in `Scripts/UI/GUI`. `CodeLibraryPanel` (hidden drawer, opened by a small tab at the middle of the right edge; opening it closes `CraftingPanel` and vice versa) is the code library: dropping an auxiliary window (not Main) by its header onto the open panel or the tab saves `Title` + `Code` through `CodeLibrary` to `Application.persistentDataPath/code_library.json` (same title overwrites) and snaps the window back; entries can be reopened as auxiliary windows (title made unique) or deleted (two clicks). Drop detection is in `CodeEditorManager` via `WindowDragger.OnDragMoved/OnDragEnded`. Windows extend `CodeEditorWindowBase` (a `VisualElement`) composed of helpers in `UI/Elements` (`CodeEditor`, `WindowDragger`, `WindowResizer`, `TitleEditor`). Keyboard input is swallowed by the UI container unless a code field was focused by mouse click (`PlayerEventBus.OnUIFocused`). UI Toolkit keyboard navigation (WASD/arrows/Tab/Enter, the same keys as camera movement) is blocked at the panel root in `CodeEditorManager.BlockKeyboardNavigation` via `focusController.IgnoreEvent`. `CodeEditorManager` also implements `IPointerOverUIProvider` (`panel.Pick` at the cursor, ignoring full-screen backgrounds); `CameraController` uses it so mouse-wheel zoom (orthographic size, clamped `minZoom`–`maxZoom`) does not fire over windows or panels. The UI is mouse-only, and code fields reject any focus that didn't start with a `PointerDown`. Keep it that way, otherwise camera keys can move focus into a code field and overwrite the code.

**Code editor internals** (`UI/Elements/CodeEditor.cs`): shared services (theme, `LuaSyntaxHighlighter`, `LuaCompletionProvider`, line-cost function) are built once in `CodeEditorManager.CreateContext()` and passed to every window as `CodeEditorContext`. Highlighting is a rich-text `Label` inserted into the `TextField`'s own `ScrollView` content container, under the field's text, which is made transparent (caret/selection colors live in `CodeEditorCommon.uss`). The highlighted text must stay character-for-character identical to the source, which is why `<` is wrapped in `<noparse>`. Line-number and line-cost gutters are aligned to the text element's `worldBound` (which already includes scroll). Command names, signatures, descriptions, and costs for highlighting/completion come from the `ILuaCommand` registry — new commands show up automatically. Quirk: after setting `TextField.value` from code, the field applies `SelectRange` only several frames later, so `CodeEditor` tracks `_pendingCursor` and reads the cursor through `CursorIndex`. Use `ReplaceRange`/`InsertText` for programmatic edits.

## Conventions

- Code comments are in Russian; save `.cs` files as **UTF-8 with BOM** (some were previously CP1251 and showed mojibake).
- Style: `[SerializeField] private` fields, `_camelCase` private members, `Debug.Assert` reference validation in a `ValidateReferences()` method, section separators like `// ─── Public API ───`.
- Classes are in the global namespace.

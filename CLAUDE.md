# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Unity **6000.4.10f1** 2D (URP) programming game (working title "CodeRogue" in `CreateAssetMenu` paths). The player doesn't control the pawn directly — they write **Lua** in in-game editor windows, and Lua calls C# commands that move the pawn, query objects, etc. Every Lua construct costs "energy". Art comes from the third-party `Assets/Tiny Swords` pack — don't modify it. All project code lives in `Assets/_Game`; the only scene in the build is `Assets/_Game/Scenes/Game/SampleScene.unity`.

Key dependencies: Lua-CSharp 0.5.5 (`Lua`, `Lua.Standard` namespaces; DLLs installed by NuGetForUnity into `Assets/Packages`, Unity glue via the `com.nuskey8.lua.unity` UPM package), UniTask, UI Toolkit (UXML/USS, no uGUI), Input System, Tilemap + Rule Tiles. Binary assets (png, dll) are in Git LFS.

## Build / verify

There are no tests, asmdefs, or lint setup. All game code compiles into `Assembly-CSharp`.

- Fast compile check without opening Unity (uses the Unity-generated, gitignored csproj):
  `dotnet build Assembly-CSharp.csproj -nologo -v q`
  The csproj lists files explicitly and is only regenerated by Unity — a **newly added** `.cs` file won't be compiled by this command until Unity regenerates the project (or you add a `<Compile Include>` line locally).
- Real verification requires Play Mode in the Unity editor.

## Architecture

**Composition root:** `Core/Level.cs` holds serialized references to every system and wires them in `Awake` in a fixed order: map generation → spawn point → player instantiate → `PlayerCommandExecutor` → fog of war → camera → objects → `LuaSandbox` → UI. Systems don't find each other; dependencies are passed via `Initialize(...)` methods, mostly as interfaces (`IMapDataProvider` implemented by `TilemapGenerator`, `IPlayerDataProvider` implemented by `PlayerConfig`). When adding a system, add a serialized field + assert + an `Initialize` call here.

**Events:** two static buses — `PlayerEventBus` (player moved, UI focus, camera, day start/end) and `UIEventBus` (energy, per-window code cost, inventory, notifications). `UIManager` is the single subscriber that pushes `UIEventBus` changes into UI elements. Because the buses are static, always unsubscribe in `OnDestroy` with named methods (not lambdas).

**Config:** tunables are ScriptableObjects in `Assets/_Game/ScriptableObjects` (`PlayerConfig`, `EnergyConfig`, `MapGenerationConfig`, `CodeEditorTheme`, `ResourceVariant`s).

**Lua pipeline** (`Scripts/Lua`):
- A command = class implementing `ILuaCommand` (usually via `PlayerCommandBase`, which supplies `Executor` and `MapData`). It declares `Name`, `EnergyCost`, and `Register(LuaState)`, which sets `state.Environment[Name] = new LuaFunction(async (context, ct) => ...)`. Pass `ct` into any awaited executor call so Stop/cancellation works.
- New commands must be registered in `LuaSandbox.RegisterCommands()`. Registering also makes `EnergyCounter` charge `EnergyCost` whenever the identifier appears in code.
- `LuaSandbox.ExecuteAsync`: auxiliary editor windows are wrapped as global functions `function <WindowTitle>(...) <code> end` (so window titles must be valid Lua identifiers — enforced by `LuaIdentifierValidator` in `TitleEditor`), then the main window code runs. Execution is cancellable (`Stop()`, the Run button toggles to Stop) and guarded by a thread-pool watchdog that cancels if the main thread is blocked longer than `freezeTimeoutSeconds` (catches infinite loops without awaits).
- Energy cost is computed statically by tokenizing code (`LuaTokenizer` → `EnergyCounter`: keyword costs from `EnergyConfig` + command costs from the registry). It is displayed per window but not deducted; only dynamic costs (harvesting) spend `PlayerEnergy` at runtime.
- `LuaModuleLoader` (`require`) and `LuaSyntaxHighlighter` exist but are not wired in.

**Depth sorting:** `DepthSortedSprite` sets `sortingOrder` of all child `SpriteRenderer`s from `transform.position.y` via `DepthSorting` (bottom of map = 1000, top = 100; range configured in `Level` right after map generation). `ResourceObject` adds it automatically and refreshes on `SetPosition`; the player gets it in `Level.SpawnPlayer` with `Dynamic = true`. The fog tilemap is forced to `DepthSorting.OverlayOrder` (2000) so it stays above all objects — keep any new world sprites inside 100–1000 and overlays above.

**Player movement:** `PlayerCommandExecutor` keeps the logical `CurrentTile` and animates tile-by-tile with UniTask; walkability comes from `IMapDataProvider`, and movement is continuous (`MoveTowardsAsync`): the target is the last land tile on the straight line (water stops immediately), and each frame the player's own non-trigger `Collider2D` is cast (`Collider2D.Cast`, its real feet shape) against other non-trigger colliders; on contact it stops `CollisionSkin` short and slides along the surface (head-on picks the side toward the target), so round objects are walked around. The command ends when the target is reached or after `PlayerConfig.stuckTimeout` seconds without getting closer. `CurrentTile` is the tile actually containing the player; returned counts are tile changes (sprites are never used for collision; the player's Rigidbody2D is Kinematic so physics never pushes it). `moveTo` steps in a straight line (no pathfinding). Each completed step publishes `PlayerEventBus.OnPlayerMoved` (fog of war reacts to it).

**Map & coordinates:** `TilemapGenerator` builds a Perlin-noise grass/water grid (`TileType[,]`) plus water padding and a fog layer. Biomes: `MapGenerationConfig.biomeConfig` (`BiomeConfig` asset, biomes inline with weight and resource list) → `BiomeMap.Generate` splits the map into noise-warped Voronoi cells, each assigned a weighted-random biome (every biome appears at least once); query with `IMapDataProvider.GetBiome(x, y)`. Use tile indices (`Vector2Int`) for game logic and convert with `TileIndexToWorld` (returns the cell **center**) / `WorldToTileIndex`. Never derive tiles by rounding `transform.position`. Objects use free map positions (`Vector2` in tile units, integers = tile centers): convert with `IMapDataProvider.MapToWorld`, get the containing tile with `MapPosition.ToTile`.

**Objects:** `ObjectGenerator` spawns `ResourceObject` prefabs (via `ObjectPool`, keyed by type) at random free positions (any point inside a walkable tile, at least `minObjectSpacing` apart, outside `spawnClearRadius` of the spawn point), per biome (randomness seeded from `IMapDataProvider.Seed`, so a fixed map seed reproduces objects too): for each `BiomeResource` it spawns `density` objects per 100 land tiles of that biome, calling `SetPosition`; placement uses only the prefab's `Collider2D` footprint (`ObjectFootprint`, computed from Box/Circle/Capsule/Polygon shape since prefab bounds are empty; no collider = a point; sprites are expected to have their pivot at the base) — every tile under it must be land and it must stay `spawnClearRadius` from the player spawn; `ResourceObject.Tile` is derived from `Position`. `ObjectManager` buckets them by containing tile for radius queries (`GetNearestObjectAt` for point lookups). Lua sees fractional `x`/`y`; `moveTo` accepts them and goes to the containing tile. Hierarchy: `ResourceObject` → `HarvestableResource` (no tool) / `ExtractableResource` (tool required) → concrete types in `Objects/Types`; drop/visuals come from `ResourceVariant`. `FindObjectsCommand.TypeMap` maps Lua type names to these classes — update it when adding a type. Each `ResourceItem` has a `durability`; harvesting costs `ResourceVariant.HarvestEnergyCost` (durability × dropAmount). `harvest(x, y)` / `harvest(obj)` (`HarvestCommand`) picks the nearest object within 0.5 of the point, checks distance from the player's tile/tool, spends runtime energy from `PlayerEnergy`, calls `Interact()` and adds the drop to `PlayerInventory` (both plain classes created in `Level`). `PlayerInventory` has `PlayerConfig.inventorySlots` fixed slots, each a stack of one `ResourceItem` up to `maxStackSize`; `harvest` fails with "inventory is full" before spending energy if the drop won't fit. Tools aren't implemented, so objects with a `RequiredTool` (tree, rabbit) can't be harvested yet.

**Crafting:** recipes are `[Serializable] CraftRecipe` entries (result + `ingredients` + `CraftingStation` + `energyCost`) edited inline in the single `RecipeBook` asset (`ScriptableObjects/Recipes/RecipeBook.asset`, assigned on `Level`); `Scripts/Editor/CraftingDrawers.cs` draws them as cards with sprite previews and edits the result item's name/sprite in place. Icons everywhere come from `ResourceItem.sprite`. `craft("name")` (`CraftCommand`) finds the recipe by result display name/itemId (case-insensitive), checks ingredients/energy, and swaps ingredients for the result atomically via `PlayerInventory.TryExchange`. Always go through `CraftRecipe.GetRequirements()` (skips empty rows, merges duplicate items) — `craft()`, the panel, and the inspector drawer all use it; `CanCraft` is what the panel highlights. Stations aren't implemented, so recipes with a station fail with "station required". `CraftingPanel` (bottom-right button + right side panel) only displays recipes; crafting is code-only.

**UI:** `CodeEditorManager` (on the `UIDocument`) creates a `window-layer` (code windows live there, below everything else), the `TopBar`, the bottom `InventoryBar`, the `CraftingPanel` (slots rendered from `UIEventBus.OnInventoryChanged` snapshots), the main window, and auxiliary "class" windows from UXML templates in `Scripts/UI/GUI`. Windows extend `CodeEditorWindowBase` (a `VisualElement`) composed of helpers in `UI/Elements` (`CodeEditor`, `WindowDragger`, `WindowResizer`, `TitleEditor`). Keyboard input is swallowed by the UI container unless a code field was focused by mouse click (`PlayerEventBus.OnUIFocused`). UI Toolkit keyboard navigation (WASD/arrows/Tab/Enter, the same keys as camera movement) is blocked at the panel root in `CodeEditorManager.BlockKeyboardNavigation` via `focusController.IgnoreEvent`. `CodeEditorManager` also implements `IPointerOverUIProvider` (`panel.Pick` at the cursor, ignoring full-screen backgrounds); `CameraController` uses it so mouse-wheel zoom (orthographic size, clamped `minZoom`–`maxZoom`) does not fire over windows or panels. The UI is mouse-only, and code fields reject any focus that didn't start with a `PointerDown`. Keep it that way, otherwise camera keys can move focus into a code field and overwrite the code.

**Code editor internals** (`UI/Elements/CodeEditor.cs`): shared services (theme, `LuaSyntaxHighlighter`, `LuaCompletionProvider`, line-cost function) are built once in `CodeEditorManager.CreateContext()` and passed to every window as `CodeEditorContext`. Highlighting is a rich-text `Label` inserted into the `TextField`'s own `ScrollView` content container, under the field's text, which is made transparent (caret/selection colors live in `CodeEditorCommon.uss`). The highlighted text must stay character-for-character identical to the source, which is why `<` is wrapped in `<noparse>`. Line-number and line-cost gutters are aligned to the text element's `worldBound` (which already includes scroll). Command names, signatures, descriptions, and costs for highlighting/completion come from the `ILuaCommand` registry — new commands show up automatically. Quirk: after setting `TextField.value` from code, the field applies `SelectRange` only several frames later, so `CodeEditor` tracks `_pendingCursor` and reads the cursor through `CursorIndex`. Use `ReplaceRange`/`InsertText` for programmatic edits.

## Conventions

- Code comments are in Russian; save `.cs` files as **UTF-8 with BOM** (some were previously CP1251 and showed mojibake).
- Style: `[SerializeField] private` fields, `_camelCase` private members, `Debug.Assert` reference validation in a `ValidateReferences()` method, section separators like `// ─── Public API ───`.
- Classes are in the global namespace.
